# AI駆動開発の実践記録 —「うちの区ちゃん」181コミットの内訳

## この文書の位置づけ

チーム内で AI 駆動開発を再現するためのナレッジである。都知事杯オープンデータ・ハッカソン2026の提出作品「うちの区ちゃん」を、個人＋コーディングエージェントで約1か月・181コミットで作った過程を、git履歴と現存ドキュメントから再構成した。

記述は git履歴・現存ドキュメント・コードで確認できる事実に限る。根拠はコミットハッシュで併記する。確認できない動機や心情は書かない。

- 第1部: 何が起きたか（時系列5フェーズ）
- 第2部: 何を型として真似るか（再現手順7ステップ）
- 第3部: 何で失敗したか（教訓6件）

対象読者は、これから AI 駆動でプロダクトを立ち上げる開発者である。作品そのものの設計は [docs/system-design/README.md](../system-design/README.md) を参照する。

### 効いた判断2: データを「捨てる基準」を先に決めた

`00-summary.md` に「データ選定の品質ゲート」として3条件を明文化した。

1. 既存ダッシュボードで答えられない「新しい問い」があるか（なければ捨てる）

3番目は最終成果物まで生き残り、AGENTS.md の実装制約「区の表現は中立・前向きにし、地域スティグマにつながる否定的ラベルを避ける」になった。

# 第2部 — 抽出した型（再現手順）

他プロジェクトで同じ進め方をするための7ステップ。各ステップに本プロジェクトの根拠を添える。

## ステップ1: 調査させるとき、結論だけでなく「捨てる基準」を書かせる

調査アウトプットに、判断基準・品質ゲート・失格条件を含めさせる。基準がないと、以後のすべての判断でAIに再説明が必要になる。

- 本件の実例: 「データ選定の品質ゲート」3条件、特に**2時間 kill test**（`00-summary.md`）
- 効果: 倫理設計の条件が最終成果物の実装制約（地域スティグマ回避）まで生き残った

## ステップ2: 調査結論を別のAIに批判させる

同一モデルに自己批判させるのではなく、別系統のモデルに read-only で結論を渡し、忖度なしの批評を依頼する。指摘を P0/P1/P2 で分類して独立ファイルに残す。

- 本件の実例: `docs/research/07-cross-check-codex.md`（MCP経由で Codex に依頼、`.mcp.json` で設定）
- 効果: 「可視化とサービスの混同」という方針レベルの誤りを実装前に発見
- 運用: 批評元のスレッドIDまで記録しており、追撃質問が可能
- **本件の失敗**: この批評記録を 7/10 の統合（`eda60bf`）で削除した。批評記録は蒸留せず原文で残す

## ステップ3: 実装の前に spec、spec の後に plan を書かせる

いきなり実装させず、設計書（spec）と実装計画（plan）を別コミットで作る。**設計変更は実装前に済ませる。**

- 本件の実例: spec 13本 + plan 9本。`4dd99ca` → `48d758a` の設計差し替えは捨てコード0行
- 判定基準: plan を読んで実装順序が一意に決まらないなら、spec が曖昧である
- 注意: `0dee10b` のように「実装計画＋仕様書の齟齬修正」を同時に行うコミットが現れる。plan を書く過程が spec の穴を見つける

## ステップ4: ドメイン型 → 純ロジック → 実データ → UI の順で作らせる

副作用のない関数を先にテスト付きで固める。UIは最後。

- 本件の実例: 7/11 10:48〜10:57 の9コミット（軸型 → 正規化 → 採点 → 最近傍 → k-means → 実データ → 図鑑UI → 診断UI）
- 演出を含むUIでも適用する: `diagnosisFlow`（`95c965c`）、`nextHeaderState`（`d20d8c6`）のように判定ロジックだけを純関数で先に切る
- 理由: 純ロジックは検証を自動化できるため、AIの生成物の正しさをその場で確定できる。UIを先に作ると正しさの判定が人間の目視に依存してボトルネックになる

## ステップ5: 演出・非決定性は最初からシードで固定する

アニメーションやランダム配置を含む機能では、乱数をシード化して決定的にする。テスト可能性が保たれる。

- 本件の実例: `31f82b3`「決定的なヒーロータイムライン、シード付きmanifest（TDD）」、`2504a38`「決定的な k-means」
- 副産物: k-means の区グループ所属はスナップショットテストで固定されており、データ更新で所属が変わるとテストが落ちて検知できる

## ステップ6: マージ前に「最終レビュー専用パス」を通す

機能実装が終わった後、レビュー指摘だけを反映する独立コミットを作る。

- 本件の実例: `8a4dd0a`（OG環境変数の警告・フォント注記・デッドコード）、`ef5497f`（死にCSS削除・シェアリンクにaria-label追加）、`aee7895`（境界テスト・再シード意図コメント・rAF解除）、`8b2ea44`（キーボードスキップ・matchMedia非対応クラッシュ・CSS重複・死んだ三項演算子）
- 傾向: AIの実装は**デッドコード・死にCSS・aria属性の欠落・rAFの解除漏れ**を残しやすい。レビュー観点をこの4点に固定すると効率がよい

## ステップ7: 同じ変更で設計書を同期し、完了した spec/plan は削除する

実装コミットとセットで設計書を更新する。完了した spec/plan は残さず削除する。

- 本件の実例: `4d69767`、`0616cc4`、`cdff760`、`1c2f5e6`、`307ec9d`（実装直後の docs 反映）
- 削除の実例: `0a61996`、`cf60e39`、`704389e`。**現在ツリーに spec/plan は0本**
- 理由: 完了済みの計画書が残ると、AIが古い計画を現行仕様として読む。AGENTS.md は「`docs/system-design/` に実装手順書や時系列の作業計画は置かない」と明記している
- 併せて: `b2fdf52`「ResultPageが直接呼ぶのは xShareUrl のみと正確化」のように、設計書の誤りを見つけたら単独コミットで直す

## 再現チェックリスト

新しいプロジェクトを AI 駆動で始めるとき、順に確認する。

- [ ] 調査アウトプットに「捨てる基準」が書かれているか
- [ ] 調査結論を別系統のAIに批判させたか。指摘を P0/P1/P2 で分類したか
- [ ] エージェント向けガイド（AGENTS.md 等）に**不変条件**を列挙したか（本件では5軸キーの順序、23区の完備、生成物の一致、2D導線の維持）
- [ ] spec → plan → 実装 の順で、それぞれ別コミットになっているか
- [ ] 純ロジックがUIより先に、テスト付きで存在するか
- [ ] 非決定性がシードで固定されているか
- [ ] 手作業の同期・コピーをテストで封じたか
- [ ] AIの性能・構成の「改善」提案を、採用前に計測したか
- [ ] 外部素材の出典・ライセンスを台帳化し、不明を `要確認` と書けるようにしたか
- [ ] マージ前に最終レビュー専用コミットを作ったか
- [ ] 完了した spec/plan を削除したか

# 第3部 — 失敗パターンと教訓

## 教訓1: AIの「最適化」提案は計測で却下する

**何が起きたか**: `9f027c4` で three.js を共有チャンク `three-vendor` へ分離し、二重バンドルを解消した。バンドル解析上は正しい最適化である。しかし Lighthouse を実測すると悪化した。

| 指標 | 統合前 | 統合後 |
|---|---|---|
| トップページ | 94 | 89 |
| 区詳細ページ | 73 | **63** |
| 転送量 | — | +359KB |

原因は、共有チャンクが2ページ分の union（832KB）になり、単一ページ訪問では不要なコードまで読み込むためである。`2d61d9d` でリバートし、`7c0ff03` で却下理由を懸念事項へ記録した。

**教訓**: 「二重バンドルは無駄」は一般論としては正しいが、単一ページ訪問が主な利用形態では成立しない。AIは一般論としての最適化を確信を持って提案する。**採用の条件を「理屈が通ること」ではなく「計測が改善すること」に置く。**

**残し方が重要**: 現在の設計書（`07-risks-and-concerns.md`）の「受容している制約」節に、数値付きで却下理由が残っている。これがないと、半年後に別のAIが同じ最適化を提案し、同じ作業を繰り返す。

## 教訓2: データ定義の誤用はAIも人間も気づかない

**何が起きたか**: `160e875` で「平均所得（課税対象所得）」を区詳細データに追加した。11分後の `04f6c12` で修正している。

誤りは**課税標準額（各種控除後の金額）を課税対象所得として使っていた**ことである。修正では、総務省「市町村税課税状況等の調」（令和6年度）〔市町村別内訳〕第11表の課税対象所得 ÷ 所得割の納税義務者数へ差し替え、raw入力も東京都再集計版の第9表から総務省公式の市町村別内訳（`J51-24-b.xlsx`）へ変更した。

**教訓**: 統計表の列名は似ている。AIは列名の字面が近い値を取ってしまい、指標の定義上の差（控除前か控除後か）を検証しない。生成された数値が「もっともらしい範囲」に収まると、レビューでも通過する。

**対策**: 数値の妥当性ではなく、**出典の表番号・列名・分母を設計書に書かせる**。本件では修正時にテスト閾値も実データで成立する値へ戻している（`3,000千円超`）。同種の修正として `4ce0804`「外国人比率の出典ラベルに%単位を明記」がある。

## 教訓3: 説明文の数値は実データから乖離する

**何が起きたか**: `178b020`「説明文の数値・順位表現を実データに合わせて修正」。キャラクター紹介文や区の説明に書かれた数値・順位が、実際のデータと合っていなかった。

**教訓**: AIが書く散文は、参照している数値が固定文字列になる。データを更新しても散文は追随しない。散文と数値の二重管理が発生している。

**対策**: 数値を含む説明文は、可能ならデータから生成する。生成できない場合（本件のAI執筆によるタイプ特徴3行、`14f7248`）は、**データ更新時に全コピーを見直す工程を運用に含める**。現在の懸念一覧には「データ更新時の全コピー中立性レビューを維持する」が残っている。

## 教訓4: 生成物の二重管理は文章では守れない

**何が起きたか**: `data/processed/*.json`（Python生成物）と `src/data/*.json`（アプリ同梱物）を同一に保つ制約が、当初 AGENTS.md の文章だけで管理されていた。`8481d0a` で `npm run sync:data` コマンド化し parityテストを追加した。

**教訓**: 「2つのファイルを同一に保つ」という制約は、ガイドに書いてあっても守られない。AIは片方だけを編集する。人間も同じ。

**対策**: コピー作業をコマンド化し、同一性をテストにする。現在のテストは `data/processed` と `src/data` のバイト単位一致を検証している。

## 教訓5: AIは性能負債を持ち込む

**何が起きたか**: `2a1acb1`「2.5MBの favicon.svg を削除し LCP画像へ `fetchpriority=high` を付与」。favicon に2.5MBのSVGが入っていた。

同種の問題が複数ある。

- `28849b5` — `WardMesh` のジオメトリを dispose せず GPUバッファをリークしていた
- `07-risks-and-concerns.md` に現存する懸念 — 3D表示がヒーロー表示時に23枚の全キャラクター画像を先行ロードする（896px版で約7.0MB）

**教訓**: AIは「動く実装」を作るが、リソースの解放・サイズ予算・読み込み優先度は指示しないと考慮しない。3D・画像・アニメーションを含む実装では特に顕著である。

**対策**: 実装完了時のレビュー観点に「dispose・サイズ上限・優先度」を固定で入れる。性能予算を数値で AGENTS.md に書く（本件では未達。懸念として残っている）。

## 教訓6: 設計書は実装より速く古くなる

**何が起きたか**: docs コミットが52本ある。それでも乖離する。

本文書を書く過程で、`07-risks-and-concerns.md` の記載2件が実測と合っていないことが判明した。

| 項目 | 設計書の記載 | 実測 |
|---|---|---|
| `npm test` | 36ファイル・208テスト | **40ファイル・251テスト** |
| `npm audit --omit=dev` | moderate 2件（`postcss` 経由） | **high 3件**（`next@15.5.20` 本体、`postcss@8.4.31`、`sharp@0.34.5`） |

依存監査のほうは深刻度の等級まで変わっており、対応方針も古くなっていた（現在は `next` と `postcss` は `npm audit fix` で解消でき、破壊的更新が必要なのは `sharp` だけである）。両方とも本文書の作成と同じ機会に修正した。

一方、同節の「52ページの静的生成」「生成物のバイト単位一致」「アセット枚数と寸法」は再実測しても記載どおりだった。**古くなったのは、外部の状態に左右される数値**（テスト数は自分たちの変更で増える、脆弱性の等級は外部の報告で変わる）であり、自分たちの成果物の構造を述べた記述は保った。

**教訓**: 設計書に「実行結果の数値」を書くと、その数値が最初に古くなる。構造の説明は長持ちするが、カウントは持たない。

**対策の方向**: 実測値は設計書に固定値で書かず、確認コマンドを書く。本プロジェクトは「同じ変更で設計書を更新する」ルールを AGENTS.md に持ち、docs 52コミットで実際に運用しているが、それでもカウント類は追随できていない。**同期コストが最も高いのは数値であると認識して、書く対象を選ぶ。**

依存監査のように外部の報告で等級が変わる項目は、記載しても必ず古くなる。書くなら「監査がexit 1になる」という状態と確認コマンドまでにとどめ、件数と等級は都度実行して読む形にするほうが保守できる。

## 失敗パターン早見表

| パターン | 兆候 | 封じ方 |
|---|---|---|
| 一般論の最適化 | 「二重バンドル解消」「共通化」などの提案が理屈で語られる | 採用前に計測。却下理由を数値付きで残す |
| 統計表の列の誤用 | 数値がもっともらしい範囲に収まっている | 表番号・列名・分母を設計書に書かせる |
| 散文中の数値の陳腐化 | データ更新後も説明文が変わらない | 生成できるものは生成。できないものは更新工程に含める |
| 生成物の二重管理 | 「2つを同一に保つ」がガイドに書かれている | コマンド化＋一致テスト |
| 性能負債 | 動作するが dispose なし・サイズ上限なし | レビュー観点に固定で追加。予算を数値化 |
| 設計書の陳腐化 | 設計書に実行結果のカウントが書かれている | 数値ではなく確認コマンドを書く |
| 完了計画書の残留 | `plans/` に完了済みファイルが残る | 完了時に削除（本件は現在0本） |
| 判断根拠の消失 | 見通し改善のためドキュメントを統合する | 批評・却下理由は蒸留せず原文で残す（`eda60bf` の反面教師） |
